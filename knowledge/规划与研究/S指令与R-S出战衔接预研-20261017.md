# S指令、出战衔接与原图复用预研

日期：2026-10-17。用户本轮要求先研究原作S及R/S衔接，战场图片沿用现有素材，站位、布阵、战前与战中剧情另行设计。本轮没有制作可玩的S，没有修改现有R、正文、Data、引擎或游戏目录。

## 结论与研究范围

原作可以提供完整的写法范本，但不能只复制一张S再换对白。需要一起设计「战前R编成 → 确认出兵 → S布阵与开场 → 玩家行动及事件 → 胜败与结算 → 战后R」。地图可复用图片及对应地形；原作的武将编号、部署槽、事件旗标、奖励地址不随图片继承。

读取本机姜维原作RS0全部58份S及8份相关R，陆抗传61份S及2份R，共129份，均通过现有解码器的结构边界检查。重点追读姜维R31/S31/R32、S03、S19、S22、S25与陆抗R04/S04、R37/S37的事件；不是宣称129份逐句精读或全部可在当前引擎运行。另核58份姜维S所引用地图，图片尺寸均与Hexzmap格数×48一致。

证据见[文件哈希与解码审计](../../project/战场设计/原作结构审计.json)、[S指令目录](../../project/战场设计/原作S指令目录.json)、[关键记录与源码指纹](../../project/战场设计/指令证据.json)、[地图索引](../../project/战场设计/原作地图索引.json)。二进制块、记录均从0计数，偏移是文件字节偏移。

原始路径：姜维 `E:\ccz-new-engine\1-工程源码\bin\Release\RS0`；陆抗 `E:\陆抗传3.1\RS`。下文源码位置相对于 `E:\ccz-new-engine\1-工程源码`；结论描述本地源码，不保证正在运行的EXE正由这一版本编译。

## 一、R如何真正进入S

姜维R31的块8开放准备菜单，块9等待出兵。关键链条：

| 阶段 | 原作证据 | 本线应如何使用 |
| --- | --- | --- |
| 战前编成 | R31 B8，0x08开交互；0x06设菜单、最多13人、强制与禁用人物 | 先确认实际入队、装备与出场名单；有Data名字不等于可出战 |
| 地图一览 | R31设置整数变量4057=54，再用0x4B给预览槽摆坐标 | 预览图与S实际地图、槽位一致；不可把预览变量留到错误阶段 |
| 确认出兵 | R31 B9，0x07等出兵标志，0x08关闭交互，再演出发对白 | 只有玩家确实确认名单，才离开准备场景 |
| 清理R菜单 | R31 B9，0x06模式0、淡出、停曲、0x0D收尾 | 不让准备菜单残留在战场上 |
| S接入 | R31自然完成后进入S31 | 现有本线R直接跳下一回，尚未接入战场 |

源码：`src/cmdbar.c:231`出兵按钮调用BuildPlayerDeployList，成功后才设置g_DeployedFlag；`src/script_cmd.c:3341`的0x07消费并清除此标志。该函数旧注释称“战斗完结后置位”，与现有调用点不符，不按注释猜用途。0x06的菜单与强制名单实现见同文件4478行附近，0x08并非名单本身。

**编号要区分“运行场景号”与“跳转参数”。** `src/script_run.c:484`按偶数2n读R_n、奇数2n+1读S_n；`src/script_cmd.c:3446`的0x11先写场景号，外层在结束时再加1（`script_run.c:645`起）。整数前缀4051为0时：

- 自然顺序：R_n → S_n → R_(n+1)。
- 0x11参数2n，下一次实际装载S_n。
- 0x11参数2n−1，下一次实际装载R_n。
- 当前R14末尾参数29，因此接R15；它没有先经过S14。

4051非0还会改变路径分段；不要从原作支线抄来后遗留。R90等功能R有自己的返回条件和变量，不宜仅为得到菜单而整块搬入。

现有构建器按“一回一个R”工作。正式嵌入乐城时，先为“马后头／放下刀的人／骆谷”建立战前、战中、战后切点，再统一编排编号、跳转与后续文件。不要现在就把S06当成第七回的正式编号：本报告中S06只是地图来源。

## 二、S的骨架与最先要学会的指令

抽查的S通常以块0初始化及开场，块1扫描战中事件，块2收尾。EEX含条件记录和嵌套事件，记录长度与块边界都要正确；不能把对白和opcode简单串接成文本。0x0C与0x0D也不是可随意互换的“结束”。

| 指令 | 已核用途 | 制作注意 |
| --- | --- | --- |
| 0x44 | 战场初始化，清本地旗标并建立玩家部署槽 | 会清0～255局部旗标；战前R结果若要带入，须另登记跨场变量 |
| 0x45 | 战场全局参数，实际读取10项 | 原作S03第三项30进入回合上限；完整字段仍须逐项核，不按旧9项注释编码 |
| 0x46 | 友军出场，每条20行，每行11项 | 空行仍须以0xFFFF补齐，首批友军从槽20起 |
| 0x47 | 敌军出场，每条80行，每行12项 | 比友军多一项隐藏参数，首批敌军从槽60起；不能套同一行宽 |
| 0x4B | 玩家部署槽的位置、朝向、隐藏状态 | 第一个参数是“槽序号”，不是Data人物ID；强制王含出场后还须核实际排槽 |
| 0x27，类型3 | 装载S地图，末参数是地图号 | m005就是5；文件名S06不表示地图6 |
| 0x19 | 胜败／目标提示文字 | 显示“保护王含”不会自动生成保护王含的失败事件 |
| 0x05／0x0B | 旗标条件／赋值 | 单次剧情配未触发条件，演过后置位；不要每轮重复对白 |
| 0x3F／0x40 | 回合条件／阵营行动阶段条件 | 回合数与阵营阶段一起考虑，免得在错误一方行动前触发 |
| 0x25／0x26／0x2E | 位置／区域／相邻人物条件 | 适合接应、越线、交谈；特殊选择器不等于普通人物ID |
| 0x42／0x43 | 通用胜／败测试 | 并不解释目标文字；任务另有失败条件时必须显式补上 |
| 0x49／0x0E | 设置胜利／失败状态 | 奖励和跨场结果在退出前写入，胜败记录互斥 |

源码主要在`src/script_cmd.c`：44约1812行，46约1923行，47约2019行，4B约2191行，19约2722行，3F约2751行，42约2877行，43约2922行，49约2965行，2E约3706行。45第三项经`deploy.c:196、591`进入deployLimit，`deploy.c:1613`使用它限制回合；变量名称带UnitCount不代表出场人数。

当前源码0x5A的卷帘部分仍是占位，只看到这个opcode不能判断“战场已完整进入并可操作”。0x43含玩家槽0阵亡及玩家全灭等通用逻辑，不能假设会按“姜维”“王含”的名字自动保护剧情人物。

三个容易错的细节：

1. 0x3F的比较模式0为“≥”，1为“＜”，其余为“＝”。`[1,0]`是第一回合起，不能当“只在第一回合”。
2. 0x2E第三参数不是接触半径；非零按邻格接触，零还涉及可攻击性判断。适合王含喊话的条件必须结合实际行动路径验证。
3. 0x77/78/79的整数或地址操作不是普通布尔旗标。原作奖励脚本写的绝对地址、4051/4057等控制变量不可盲抄；本线919等已有用途，不能随意重占。

## 三、原作值得迁移的事件组织

**先满足战果，再撤到出口。** 姜维S19，B1 r6，偏移0x5A6C，以0x25 `[0,0,19]`检查指定人物位置，还要求旗标8已真、22未真；随后撤退对白、离场及胜利处理。可学的是“先完成任务才可撤出”，不能删掉前置旗标，只剩走到格子就通关。

**战中对话解释正在发生的局势。** 姜维S25，B1 r2，偏移0x5455，0x3F `[3,2]`精确到第三回合，并检查单次旗标11。司马昭、钟会关于文钦与诸葛诞的对话放在战局节点里。迁移时，让玩家先看见行动，再用人物反应讲清关系，不在每轮开头额外上一段政治课。

**接触能触发剧情及实际状态变化。** 姜维S03，B1 r6，用0x2E `[2,222,1]`配单次旗标触发接触事件，后接状态改变。可借条件结构，不照搬这两个Data编号。

**目标会随阶段刷新。** 姜维S22有中途变化的目标文本；陆抗S37在B1 r27把目标刷新为全灭敌军，后续另有胜利事件。0x19目标文字和实际判定必须一起改。陆抗S04写明保护王平、陆抗，也适合研究“主目标以外还保护谁”的表达；其武将、兵种与资源号不能跨MOD原样套。

## 四、沿用图片，也必须沿用匹配的地形

S地图图片由`src/battlemap.c:171、339`读取`map/mNNN.JPG`，每格48像素；格点与地形来自`Hexzmap.e5`对应节（`src/deploy.c:363`起）。头两字节各除以3得到宽高，再取宽×高的地形数组。坐标左上为(0,0)，x向右、y向下。

Pmap是R场景格点，不能拿它检验S。图片像素匹配地形尺寸只证明网格一致；是否能走、要多少移动力还取决于兵种和特技，见`src/battle_deploy.c:218、1030`。城墙画着缺口不一定就能通行，也不能用R的斜角坐标直接摆S人物。

本次候选：姜维原作S06引用的m005，24×24格，1152×1152像素。城外有展开空间，西门可承载接触与接应，北门可承载贾充撤离；不更画城墙，不继承原关部队。m054（S31，40×32）更适合关口，不为乐城样关强行套大图。

具体功能布局见[乐城样关预研](../../project/战场设计/乐城样关预研.md)、[候选坐标与检查](../../project/战场设计/乐城候选布阵.json)。已经检查16个示意点不越界、不重叠，并检查两条候选路径在选定地形集合上连通。尚未检查兵种耗点、弓箭射程、AI堵路和难度；图上的兵数只是功能代表，不是正式出战表。

## 五、先验证什么，再扩成完整关卡

最小验证顺序：准备菜单确认名单 → 玩家槽正确落位 → 接触只触发一次 → 旧卒转阵及状态保留 → 一条胜利、一条失败都能结束 → 战后R正确装载 → 战中存读档不重复倒戈、不重复奖励。完成后再加多支敌军、回合压力、分支对话与评价。

目前最需要小样验证的是“旧卒由敌转友”。0x3B是非战场永久入队逻辑；0x54在当前源码不能据名称就当阵亡判定；0x55实际是复活／重新出场相关处理，不能默认保留血量和行动权。还没有确认可直接复用、状态完整的转阵指令组合。先在隔离样关验证，再决定用哪种表示，不能写一段看似可编译的伪指令冒充已实现。

正式制作还要补：本线可战人物、兵种装备、双方等级基准；局部旗标与跨场结果登记；关键人物负伤／失败规则；贾充撤离时机；战前存档与战中存档的恢复。旧存档可能带有旧人物和队伍状态，修改Data不保证自动刷新存档，这一点也要纳入入队测试。

本轮止于预研，未分配正式S编号、未重新切割十六回、未修改运行目录。研究记录不等于实机通过。
